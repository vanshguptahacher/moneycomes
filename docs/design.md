# Design Strategy & UI Evolution — Expense Sharing App

## Compatibility Baseline (Locked)

This project uses the following mobile/build baseline unless explicitly changed after a compatibility review:

- **Expo SDK:** 56.x (stable)
- **React Native:** 0.85.x (the React Native line targeted by Expo SDK 56)
- **Expo workflow:** Expo Prebuild / Continuous Native Generation (CNG)
- **Node.js development:** Node 25 may be used for local development; it is not treated as an officially supported Expo baseline.
- **Node.js build/CI fallback:** Node 22 LTS is the documented, conservative fallback for Expo/EAS/CI environments.
- **Android architecture:** Use the native configuration generated by Expo SDK 56; do not manually mix native templates from another SDK.
- **Android Gradle:** Let Expo Prebuild generate and maintain the SDK-56-compatible Gradle/Android Gradle Plugin versions. Do not manually pin Gradle or AGP unless an explicit compatibility test requires it.
- **Java:** Use the JDK version required by the SDK-56-generated Android template; verify with the generated project before changing it.
- **Reanimated:** Install the Expo SDK 56-compatible version through `expo install`, together with `react-native-worklets`; never manually force an unrelated Reanimated major version.

### Dependency rule

Use `npx expo install` (or the equivalent pnpm Expo install command) for Expo-managed native dependencies so versions are resolved for the selected SDK. Avoid `latest` for native dependencies.

### Native regeneration rule

After changing Expo/native dependencies, regenerate native projects with Expo Prebuild and then build. Do not hand-edit generated native files unless the change is intentionally required and documented.

### Node 25 rule

Node 25 is allowed for local development, but compatibility must be validated by the project's actual typecheck, Metro, Prebuild, and Android build. If a tooling issue is Node-25-specific, switch this project to Node 22 LTS rather than changing Expo/RN versions or patching native dependencies blindly.


> **Purpose:** This document defines the visual-development strategy for the expense-sharing app.
>
> **Most important decision:** Do **NOT** try to make the app visually different on day one.
>
> First build a complete, reliable, functionally correct Splitwise-style application. Once the functionality, data model, calculations, navigation, and workflows are stable, redesign the application **screen by screen** into a more professional and distinctive product.
>
> **Design evolves gradually. Logic comes first.**

---

# 1. Core Design Philosophy

The project will follow a two-stage design strategy:

```text
STAGE 1
Functional Splitwise-style App
        ↓
STAGE 2
Professional + Distinctive Design
```

The first objective is NOT originality.

The first objective is:

> **Make the complete app work like the reference product.**

Only after the functionality is stable should the visual identity evolve.

This approach reduces risk because the team can verify:

- navigation,
- authentication,
- groups,
- friends,
- expenses,
- splitting,
- balances,
- settlements,
- currencies,
- activity,
- account/settings,
- and backend synchronization

before introducing major visual changes.

---

# 2. Design Development Rule

The project must follow:

> **Functionality first → familiar UI → validation → gradual redesign → final premium UI.**

Do not attempt a complete visual transformation while the underlying product is still unstable.

The design team/developer should never spend days polishing a screen whose underlying workflow does not work.

---

# 3. Stage 1 — Reproduce the Familiar Product Experience

## Objective

Create a functionally complete application with the same general user experience and information architecture as Splitwise.

This does **not** mean copying proprietary assets, branding, source code, or exact visual implementation.

It means reproducing the **familiar product concepts and workflows** needed for an expense-sharing app.

## Stage 1 priorities

1. Correct functionality.
2. Correct data flow.
3. Correct financial calculations.
4. Correct navigation.
5. Correct forms.
6. Correct API behavior.
7. Correct database behavior.
8. Basic usable UI.
9. Reliable loading/error/empty states.
10. Testing.

Visual uniqueness comes later.

---

# 4. Stage 1 UI Goal

The first UI should be:

- simple,
- familiar,
- functional,
- predictable,
- easy to test,
- easy to redesign later.

Do NOT over-engineer the visual system at this stage.

The UI should be good enough to:

- understand the workflow,
- verify functionality,
- test edge cases,
- demonstrate the product,
- identify UX problems.

# 6. Stage 1 — Preserve Familiar Information Architecture

The first implementation should intentionally feel familiar.

Users should understand:

- where groups are,
- where friends are,
- where expenses are added,
- where balances are shown,
- where settlements happen,
- where activity is located,
- where settings are located.

Do not move everything around merely to make the app look different.

Familiarity is an advantage during the functional-development phase.

---

# 7. Stage 1 — Expense Workflow

The expense workflow is the most important user flow.

It should follow a familiar sequence:

```text
Add Expense
   ↓
Who/Which Group?
   ↓
Description
   ↓
Amount
   ↓
Paid By
   ↓
Split
   ↓
Participants
   ↓
Currency / Date / Note
   ↓
Save
   ↓
Updated Balance
   ↓
Activity
```

The first goal is to make this flow completely reliable.

Do not redesign the workflow radically before it is stable.

---

# 8. Stage 1 — Split Workflow

The first version should make all required split methods functional.

Supported:

- Equally.
- Unequally / Exact.
- By percentages.
- By shares.
- By adjustment.

The UI should clearly expose these choices.

The actual calculation must be handled by the financial domain engine described in:

- `architecture.md`
- `tech_specs.md`
- `quality_assurance.md`

The screen itself must not become the source of truth.

---

# 9. Stage 1 — Financial UI Language

Use simple language from the beginning.

Preferred:

- `You get`
- `You pay`
- `Rahul owes you ₹500`

- `Owned by you`
- `Receivable`
- `Payable`

unless technical/accounting terminology is specifically needed in an internal/admin context.

# 34. Animation Strategy

Animations should communicate state and hierarchy.

Good uses:

- screen transitions,
- bottom sheets,
- button feedback,
- list insertion,
- balance updates,
- success states.

Avoid:

- animation on every element,
- long transitions,
- distracting effects,
- animations that block financial actions.

Use Reanimated where appropriate.

Use Haptics for meaningful interactions, not every tap.

---

# 35. Gesture Strategy

Use Gesture Handler for interactions that benefit from gestures.

Examples:

- bottom-sheet interaction,
- swipe actions where useful,
- dismiss gestures.

Do not add gestures merely because they are technically possible.

Important actions should always have an accessible non-gesture alternative.

---

# 36. Responsive Design

The application must work across supported phone sizes.

Check:

- small screens,
- large screens,
- safe areas,
- keyboard,
- long names,
- large amounts,
- long group names,
- many participants,
- accessibility text scaling.

Never allow financial amounts to be clipped.

---

# 37. Dark Mode

If dark mode is implemented, it should use the same design tokens.

Do not simply invert colors.

Validate:

- contrast,
- financial semantics,
- cards,
- dialogs,
- inputs,
- navigation,
- charts if present.

Dark mode should be a coherent design system, not a filter.

---

# 38. Accessibility

Every redesigned screen must preserve:

- readable text,
- contrast,
- touch targets,
- screen-reader labels,
- semantic states,
- non-color-only communication.

Examples:

# 40. One Screen at a Time Rule

Do not redesign all pages simultaneously.

For each page:

```text
1. Existing functional screen
        ↓
2. Document current behavior
        ↓
3. Preserve behavior
        ↓
4. Redesign visual structure
        ↓
5. Implement
        ↓
6. Test
        ↓
7. Compare old vs new behavior
        ↓
8. Approve
        ↓
9. Move to next screen
```

This is the preferred workflow.

---

# 41. No Logic Changes During Visual Redesign

While redesigning a page, do not modify:

- balance formulas,
- expense calculations,
- settlement calculations,
- currency rules,
- database semantics,
- API contracts

unless the user explicitly requests a functional change.

A UI redesign should remain a UI redesign.

If a technical problem genuinely requires a business-logic change, document it before proceeding.

# 43. What “Professional” Means

Professional does NOT mean:

- more gradients,
- more animations,
- more colors,
- more cards,
- more effects,
- more 3D.

Professional means:

- clear hierarchy,
- deliberate spacing,
- consistent components,
- excellent typography,
- predictable interactions,
- restrained motion,
- accurate information,
- polished edge states.

# 44. What “Different” Means

The app should eventually develop its own identity through:

- typography,
- color system,
- card language,
- financial visualization,
- component shapes,
- interaction patterns,
- motion,
- iconography,

# 49. Design Definition of Done

A redesigned screen is complete only when:

- [ ] Original functionality still works.
- [ ] Existing API behavior still works.
- [ ] Financial calculations are unchanged.
- [ ] Navigation works.
- [ ] Loading state works.
- [ ] Empty state works.
- [ ] Error state works.
- [ ] Accessibility is checked.
- [ ] Responsive layout is checked.
- [ ] Relevant tests pass.
- [ ] Visual hierarchy is improved.
- [ ] The screen matches the design system.

---

# 50. Final Design Principle

The project should **not** start by asking:

> “How can we make this look completely different from Splitwise?”

It should start by asking:

> “Can we make the entire expense-sharing product work correctly and reliably?”

Then:

> “Can we make each screen easier to understand?”

Then:

> “Can we make each screen more professional?”

And finally:

> “Can we create a distinctive visual identity without making the familiar product harder to use?”

Therefore the definitive strategy is:

## **FUNCTION FIRST → FAMILIAR UI → TEST → REDESIGN ONE SCREEN AT A TIME → PROFESSIONAL IDENTITY**

The final application should preserve the user's familiar mental model while delivering a significantly more polished, modern, professional experience.
