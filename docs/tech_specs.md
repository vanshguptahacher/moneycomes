# Technical Specification — Expense Sharing App

## Compatibility Baseline (Locked)

This project uses the following mobile/build baseline unless explicitly changed after a compatibility review:

- **Expo SDK:** 56.x (stable)
- **React Native:** 0.85.x (the React Native line targeted by Expo SDK 56)
- **Expo workflow:** Expo Prebuild / Continuous Native Generation (CNG)
- **Node.js development:** Node 25 may be used for local development; it is not treated as an officially supported Expo baseline.
- **Node.js build/CI fallback:** Node 22 LTS is the documented, conservative fallback for Expo/EAS/CI environments.
- **Android architecture:** Use the native configuration generated by Expo SDK 56; do not manually mix native templates from another SDK.
- **Android Gradle:** Let Expo Prebuild generate and maintain the SDK-56-compatible Gradle/Android Gradle Plugin versions. Do not manually pin Gradle or AGP unless an explicit compatibility test requires it.
- **Java:** Use the JDK version required by the SDK-56-generated Android template; verify with the generated project before changing it.
- **Reanimated:** Install the Expo SDK 56-compatible version through `expo install`, together with `react-native-worklets`; never manually force an unrelated Reanimated major version.

### Dependency rule

Use `npx expo install` (or the equivalent pnpm Expo install command) for Expo-managed native dependencies so versions are resolved for the selected SDK. Avoid `latest` for native dependencies.

### Native regeneration rule

After changing Expo/native dependencies, regenerate native projects with Expo Prebuild and then build. Do not hand-edit generated native files unless the change is intentionally required and documented.

### Node 25 rule

Node 25 is allowed for local development, but compatibility must be validated by the project's actual typecheck, Metro, Prebuild, and Android build. If a tooling issue is Node-25-specific, switch this project to Node 22 LTS rather than changing Expo/RN versions or patching native dependencies blindly.

# 22. Expense Split Engine

The split engine must be deterministic and framework-independent.

Conceptual interface:

```ts
type SplitMethod =
  | "equal"
  | "exact"
  | "percentage"
  | "shares"
  | "adjustment";

type SplitInput = {
  totalMinor: bigint | number;
  currency: string;
  participants: Participant[];
  method: SplitMethod;
  values: unknown;
};

type SplitResult = {
  allocations: Allocation[];
  totalMinor: bigint | number;
};
```

The exact types must match the project's money strategy.

---

# 23. Equal Split Algorithm

Input:

```text
total = T
participants = N
```

Base allocation:

```text
floor(T / N)
```

Remainder:

```text
T % N
```

The remainder must be distributed using a deterministic rule.

Example:

```text
₹100 / 3

base = ₹33
remainder = ₹1

allocation:
A = ₹34
B = ₹33
C = ₹33
```

The exact remainder ordering must be documented and tested.

---

# 24. Exact Split Algorithm

User provides explicit allocations.

Invariant:

```text
sum(allocations) == total
```

Reject:

```text
sum < total
sum > total
negative values
invalid participants
```

Do not silently normalize invalid input.

---

# 25. Percentage Split Algorithm

Input percentages must satisfy the product-defined rule, normally:

```text
sum(percentages) == 100%
```

Calculate each allocation using integer-safe arithmetic.

Rounding must be deterministic.

Final allocations must reconcile exactly to the total.

---

# 26. Shares Split Algorithm

For shares:

```text
totalShares = sum(all shares)
```

Allocation is proportional to:

```text
participantShares / totalShares
```

Use integer-safe calculation and deterministic remainder handling.

Reject:

- negative shares,
- invalid totals,
- invalid participants.

---

# 27. Adjustment Split Algorithm

Adjustment modifies the base allocation according to the documented product rules.

The final result must still satisfy:

```text
sum(final allocations) == total
```

Every adjustment must be validated before persistence.

---

same output

# 32. Idempotency

Financial mutation endpoints should support idempotency where required.

Example:

```http
Idempotency-Key: <unique-client-generated-key>
```

The server must ensure repeated requests with the same key do not create duplicate financial effects.

This protects against:

- double taps,
- retries,
- network timeouts,
- app restarts.

# 59. API Authorization Example

```ts
const session = await requireSession(c);

const expense = await getExpense(expenseId);

if (!expense) {
  throw notFound();

await requireExpenseAccess(session.user.id, expense);

```

Never:

```ts

```

without an authorization check on protected data.

# 60. Expense Creation Example

Conceptual server flow:

```ts
const session = await requireSession(c);

const input = expenseSchema.parse(await c.req.json());

await authorizeExpenseContext(session.user.id, input);

const split = calculateSplit(input);

await db.transaction(async (tx) => {
  const expense = await insertExpense(tx, input);

  await insertSplits(tx, expense.id, split);

  await insertActivity(tx, {
    type: "expense.created",
    actorId: session.user.id,
    entityId: expense.id
  });
});
```

The exact implementation should follow repository conventions.
