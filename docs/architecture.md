# ARCHITECTURE.md — Expense Sharing App

## Compatibility Baseline (Locked)

This project uses the following mobile/build baseline unless explicitly changed after a compatibility review:

- **Expo SDK:** 56.x (stable)
- **React Native:** 0.85.x (the React Native line targeted by Expo SDK 56)
- **Expo workflow:** Expo Prebuild / Continuous Native Generation (CNG)
- **Node.js development:** Node 25 may be used for local development; it is not treated as an officially supported Expo baseline.
- **Node.js build/CI fallback:** Node 22 LTS is the documented, conservative fallback for Expo/EAS/CI environments.
- **Android architecture:** Use the native configuration generated by Expo SDK 56; do not manually mix native templates from another SDK.
- **Android Gradle:** Let Expo Prebuild generate and maintain the SDK-56-compatible Gradle/Android Gradle Plugin versions. Do not manually pin Gradle or AGP unless an explicit compatibility test requires it.
- **Java:** Use the JDK version required by the SDK-56-generated Android template; verify with the generated project before changing it.
- **Reanimated:** Install the Expo SDK 56-compatible version through `expo install`, together with `react-native-worklets`; never manually force an unrelated Reanimated major version.

### Dependency rule

Use `npx expo install` (or the equivalent pnpm Expo install command) for Expo-managed native dependencies so versions are resolved for the selected SDK. Avoid `latest` for native dependencies.

### Native regeneration rule

After changing Expo/native dependencies, regenerate native projects with Expo Prebuild and then build. Do not hand-edit generated native files unless the change is intentionally required and documented.

### Node 25 rule

Node 25 is allowed for local development, but compatibility must be validated by the project's actual typecheck, Metro, Prebuild, and Android build. If a tooling issue is Node-25-specific, switch this project to Node 22 LTS rather than changing Expo/RN versions or patching native dependencies blindly.

# 1. Architecture Objective

This document defines the technical architecture for Phase 1 of the expense-sharing application.

The architecture must support:

- A modern React Native mobile application.
- Splitwise-style core functionality.
- A new Dashboard/Home screen.
- Reliable financial calculations.
- Secure authentication and authorization.
- PostgreSQL as the authoritative database.
- Self-hosted deployment on Oracle Cloud.
- Docker-based infrastructure.
- Offline-aware mobile behavior.
- Receipt/file storage.
- Notifications.
- Future UPI settlement integration.
- Future Phase 2 architectural evolution.

The architecture should remain intentionally simple during Phase 1.

> **Do not introduce complex infrastructure unless the current requirements justify it.**

# 2. Core Architecture Principles

## 2.1 Server Is the Source of Truth

The backend and PostgreSQL database are authoritative for:

- Expenses
- Splits
- Balances
- Payments
- Settlements
- Membership
- Permissions
- Financial totals

The mobile client may calculate previews, but authoritative financial state must come from the server.

---

## 2.2 Separate UI From Business Logic

Do not put expense calculations directly inside React components.

Use a dedicated expense engine:

```text
packages/expense-engine/
```

UI:

```text
React Native
      ↓
Hooks / Services
      ↓
API
      ↓
Backend
      ↓
Expense Engine / Services
      ↓
PostgreSQL
```

---

## 2.3 Database Integrity First

Financial mutations must be transactional.

For example:

```text
BEGIN
  Create expense
  Create participants
  Create splits
  Update required balance state
  Create activity event
COMMIT
```

If anything fails:

```text
ROLLBACK
```

Never leave partially created financial records.

---

## 2.4 Phase 1 Stability

Phase 1 intentionally keeps the architecture straightforward.

Do not introduce:

- Microservices
- Kubernetes
- Kafka
- Elasticsearch
- Complex event sourcing
- Distributed caches
- Complex service meshes

unless a later requirement explicitly demands them.

# 16. Authorization

Authentication answers:

> Who are you?

Authorization answers:

> Are you allowed to access this resource?

Every protected request should verify authorization.

Example:

```text
GET /groups/123
```

Server checks:

```text
Authenticated?
   ↓
User is member of group 123?
   ↓
YES → return group
NO  → 403
```

Never rely on client-side navigation restrictions alone.

# 26. UPI Architecture

UPI should be treated as an external payment integration.

Conceptual flow:

```text
App
 ↓
Create settlement intent
 ↓
UPI/payment flow
 ↓
External payment app/provider
 ↓
Payment result
 ↓
Reliable verification
 ↓
Backend
 ↓
Settlement confirmation
 ↓
PostgreSQL
```

Important:

- Opening a payment app is not payment confirmation.
- Never trust client-only success callbacks as authoritative proof.
- Provider-specific verification must be implemented before marking a payment settled.
- Keep UPI integration isolated behind a payment service interface.

Example:

```text
PaymentProvider
├── createPaymentIntent()
├── verifyPayment()
└── getPaymentStatus()
```

This allows the provider to be changed later.

# 51. Database Query Rules

Avoid:

- N+1 queries
- SELECT * when unnecessary
- Unbounded activity queries
- Repeated balance calculations in multiple services

Prefer:

- Explicit columns
- Joins where appropriate
- Indexed filters
- Batched queries
- Reusable query functions

---

# 52. Financial Consistency

For a mutation:

```text
Request
 ↓
Validate
 ↓
Authorize
 ↓
Begin transaction
 ↓
Apply financial changes
 ↓
Write activity
 ↓
Commit
```

If failure:

```text
Rollback
```

Never return success before the required transaction commits.

---

# 53. Event / Activity Consistency

Activity records related to financial mutations should be created inside the same database transaction when possible.

Example:

```text
Expense transaction
├── Expense
├── Participants
├── Splits
└── Activity
```

This prevents an expense from succeeding while its corresponding activity event silently fails.

---

# 54. API Security Boundaries

Never allow the client to directly:

- Modify another user's balance
- Modify arbitrary group membership
- Mark an arbitrary payment as verified
- Access another user's private receipt
- Write directly to PostgreSQL
- Bypass server validation

All sensitive operations pass through authorized backend services.

---

# 55. Dependency Strategy

Prefer stable, well-maintained libraries.

Avoid adding a dependency for a feature that can be implemented simply with the existing stack.

Before adding a new dependency:

1. Check whether an existing library already handles the requirement.
2. Check compatibility with Expo Prebuild.
3. Check maintenance status.
4. Check licensing.
5. Check bundle/runtime impact.
6. Document why it is needed.

# 65. Time and Date Handling

Server:

- Store timestamps in UTC.

Client:

- Display in user's local timezone.

Expense dates should distinguish between:

- Expense date
- Creation timestamp
- Updated timestamp

Do not use server creation time as the expense date automatically when the user explicitly chooses another date.

- Expense creation
- Payment
- Settlement

```text

 ↓
Server
 ↓
Success → keep
Failure → rollback
```

# 70. Offline Financial Mutations

Offline expense creation may be supported.

Rules:

- Generate client request ID.
- Store draft/mutation locally.
- Sync later.
- Server validates again.
- Server prevents duplicate creation.
- UI clearly shows pending/syncing status.

Do not show an offline payment as permanently completed.

# 75. Architecture Acceptance Criteria

The architecture is acceptable when:

- Mobile and backend are cleanly separated.
- PostgreSQL is the source of truth.
- Financial logic is centralized.
- Financial mutations are transactional.
- Client cannot bypass authorization.
- API is typed and validated.
- Docker deployment works.
- PostgreSQL data persists across container restarts.
- HTTPS works.
- Backups work.
- Restore has been tested.
- Offline cache does not corrupt server state.
- Duplicate financial requests are prevented.
- Dashboard uses existing domain data rather than a second financial truth.
- Phase 1 remains simple enough to maintain.

# 77. Claude Code Implementation Rules

Claude Code must treat this document together with `prd.md` as the technical source of truth.

Before making architectural changes:

1. Inspect the existing repository.
2. Identify existing architecture.
3. Reuse working code.
4. Do not introduce unnecessary dependencies.
5. Keep Phase 1 architecture simple.
6. Preserve reference product behavior.
7. Keep business logic independent of UI.
8. Keep financial calculations deterministic.
9. Keep PostgreSQL authoritative.
10. Use transactions for financial mutations.
11. Validate on both client and server.
12. Enforce authorization on the server.
13. Never expose PostgreSQL publicly.
14. Persist Docker database storage.
15. Maintain migrations.
16. Maintain backups.
17. Add tests for financial logic.
18. Run typecheck/lint/tests after meaningful changes.
19. Document major architectural decisions.
20. Do not silently introduce Phase 2 architecture.

---

# 78. Architecture Mantra

> **Simple now. Correct always. Secure by default. Easy to scale later.**

Phase 1 should not try to solve the architecture of a company with millions of users.

It should create a strong, clean foundation that can grow without forcing unnecessary complexity today.
